## Reviewed issues and local corrections

| Issue and user consequence | Local fix and evidence |
| --- | --- |
| **Batch normalization changed real EVC behavior.** An initially enabled collateral followed by enable/disable ends disabled; removing both leaves it enabled. Calls can also emit events, schedule checks or affect intervening operations. | Removed state-transition normalization from `executionService.ts`; merge retains exact call order, destination, value and context, including repeated calls. `batchComposition.test.ts` checks all 1,555 sequences of length ≤4 over six symbols, 7,465 partitions and eight initial states. `EvcSemantics.t.sol` reproduces the initial-state counterexample on actual EVC code. |
| **Simulation collapsed separate EVC transactions into a single deferred-check boundary.** A failing first transaction could appear valid if a later transaction repaired its collateral state. | `simulate.ts` rejects more than one `evcBatch`. Callers explicitly merge for atomic execution or simulate subsequent transactions after confirming the preceding state. Actual EVC fixture confirms separate disable fails while one disable/enable batch succeeds. |
| **Orphaned Permit2 approvals could prompt signatures/transactions before being silently discarded.** A pending permit followed by a direct call, or an end-of-plan permit, had no EVC insertion point. A late wrong-chain direct call could also follow already-sent prerequisites. | `execute.ts` validates the complete resolved plan before wallet callbacks. Regression covers raw and already-resolved paths and confirms zero signatures, transactions or receipt waits for invalid boundaries. Materialization already rejected missing insertion points. |
| **Repeated Permit2 allowance keys could produce invalid nonce sequences.** Raw execution read the same current nonce for two pending permits consumed in one batch. Materialized prechecks conflict with anticipated later nonces when the optional pinned-nonce revalidation is enabled. | Raw/prepared execution rejects duplicate keys before one EVC batch. Materialization conservatively rejects repeated keys across requests; explicit successive nonce scheduling with revalidation disabled was not inherently invalid. See E04 for that compatibility restriction. |
| **Populated account/wallet state could be reused on another chain or for another approval owner.** Plugin processing could consume a foreign-chain Account snapshot; allowance resolution could use a different wallet's state. | `assertAccountChain` covers plugin processing/prefetch, prepare, raw/prepared simulate/estimate/execute, and materialization. Approval resolution checks `Wallet.chainId` and every requirement's owner before mutating the plan. Tests cover all public execution entry points and preserve inputs on rejection. Bare address inputs still require the caller's wallet callbacks to use the requested chain/account. |
| **Address casing changed protocol paths.** A checksummed current controller and lowercase equal vault could emit `disableController`, which fails with outstanding debt; equal vault/asset inputs could choose a different-vault repayment path. Lowercase approval spenders could miss existing allowances. | Normalized address comparisons in `encode.ts` and planner branches, and normalized wallet allowance keys. Borrow and same-vault repay regressions inspect emitted calldata; allowance regression confirms no redundant approval. |
| **Mint approval rounded required assets down.** A fractional supplied rate could authorize one unit less than needed. | Final multiplication now rounds up, but prior WAD-rate quantization can still understate approval at the same timestamp. E07 gives a current one-unit-versus-two counterexample; this remains an estimate, not exact `previewMint`. |
| **Original EulerEarn asset-denominated redeem treated assets as shares one-for-one.** With accrued yield it could redeem too many shares/assets or revert. The former underdelivery example applied to an intermediate local preview fix, not original main. Earn source line 608 states its exchange rate remains at least one; E08 recomputes the example including virtual amounts and fee shares. | Populated Earn asset requests now encode exact `withdraw(assets,receiver,owner)`; explicit shares remain `redeem`. This avoids both the original one-for-one error and the intermediate fee-incomplete preview. Snapshot display conversions remain fee-incomplete. |
| **EVC-only operations were missing health/read dependencies.** Even idempotent EVC mutations schedule account checks; raw `disableController(account)` addresses the decoded account and removes only `msg.sender`, not every controller. Reordering collateral also schedules a check. | `healthCheckSets.ts` recognizes all five mutations and EVault `disableController()`, includes decoded accounts, and conservatively retains controllers for raw EVC disable. Optional fourth `evcAddress` binds selector interpretation to the deployed destination; omitted address retains documented legacy inference. `simulate.ts` now includes controller reads for EVC-only disable/reorder and ignores their selectors at unrelated destinations. Utility and simulation regressions cover these cases; actual EVC fixture confirms idempotent scheduling. |
| **Malformed decoded provider results could report success.** This is defensive validation: normal viem decoding already rejects missing/truncated ABI bytes, and pinned EVC returns all arrays. | `runSimulation` checks the decoded shape and call-result count. Tests inject decoded provider results; E10 distinguishes these from ordinary RPC corruption. |
| **Allowance diagnostics incorrectly required both transfer routes for EVK and omitted token→Permit2 allowance.** The first local OR fix overgeneralized EVK's fallback to Earn/periphery helpers, which can select Permit2 and propagate its failure. | Rechecked diagnostics distinguish EVK fallback from Earn/Securitize/configured-verifier preference, verify the configured Permit2 getter, and report unknown routes through `allowanceDiagnosticsUnavailable` with `canExecute:false`. E11 documents tests, extra reads and the remaining approval resolver direct-allowance shortcut; detection is not automatic resolution. |
| **Deposit-all simulation changed the amount being deposited.** Literal maxUint256 approval requirements forged an impossible token balance; EVK `deposit(max)` then read that balance and failed its assets-width conversion. | Both state-override entry points retain real token balances whenever a token has a max requirement, including mixed fixed/max requirements. They keep the token in snapshot reads without forging it; diagnostics use current balance for max requirements. Tests cover all ordering/multiplicity cases and confirm no balance probing or storage override. Actual deposit-all semantics remain state-dependent. |
| **Override composition discarded caller-supplied code/full storage.** This undermined simulations relying on those overrides. Duplicate slots were SDK representation cleanup, not a separately established RPC bug: installed viem already serializes them with later values winning. | `mergeStateOverrides` preserves code/full state, applies sequential replacement/patch rules and deduplicates slots. Tests cover zero/empty replacements, ordering and immutability; E13 distinguishes the confirmed loss from cleanup. |
| **`noAllowanceOverride` behaved differently across paths.** The fast path still probed ERC20 allowances; other paths omitted documented deterministic Permit2 storage. | Both helpers emit Permit2 storage without ERC20 probes when the flag is set. Tests cover balance override on/off, sufficient supplied wallet balances and both entry points. |

## Module inventory and checked invariants

- `executionService.ts`: planner families, cleanup, same-asset migrations, CoW plan construction, plugin/preparation lifecycle, approvals, grouping/flattening. Checked deposit/withdraw/redeem/borrow/repay call contexts, controller transitions, maximum-amount sentinels, share-sourced collateral, debt receivers and cleanup destination. CoW HTTP submission and external migration authorization are separately reviewed by the swap/migration agent.
- `encode.ts`: all exported encoder families. Compared operation signatures and ordering to EVC/EVK/periphery, including EVC self-call context, `repayWithShares`, `transferFromMax`, exact-output repayment and final verification. Interest cushions and quote limits remain caller/state-dependent.
- `execute.ts`: sequential send/receipt behavior, raw versus prepared resolution, Permit2 nonce reads/signatures, total native value, error propagation and complete-plan preflight. The callback implementation owns wallet chain/account selection and signing policy.
- `materializedExecution.ts`: pinned composition inputs, deterministic immutable outputs, request/signature association, exact dispatch, failure terminality and pre-broadcast nonce revalidation. Reviewed artifacts are trusted application inputs; this is not artifact provenance authentication. Repeated Permit2 keys now fail before unsupported scheduling.
- `simulate.ts`: one-transaction boundary, action/read mapping, observed operation layers, deferred account/vault checks, missing results, optional direct-call independence, wallet deficits, vault-type lookup and snapshot construction. Simulation includes additional lens calls and synthetic state; it is not identical to an unmodified final transaction.
- `executionServiceTypes.ts`, `index.ts`, `tokenApprovalReset.ts`: public context/quantity contracts, exports, prepared-envelope discriminator and mainnet USDT reset policy. The discriminator is a structural tag, not runtime authentication. The reset list does not claim compatibility with every nonstandard token.
- `abis/*`: inventoried callable signatures and relevant tuple shapes. **44/44 EVC function signatures, output types and mutability match compiled pinned upstream** via `check-evc-abi.mjs`. EVault, Permit2, swapper/verifier and CoW wrapper shapes were inspected against source/use sites; the entire event/error ABI and every deployed contract were not proven equivalent.
- `healthCheckSets.ts`: checked accounts, controller/collateral state tracking, unrelated account/vault behavior, destination discrimination and existing account dependencies. Direct EVC disable uses a conservative superset because the utility does not authenticate its caller.
- `subAccounts.ts`: all 256 XOR-derived addresses share the 19-byte owner prefix; ID/range boundaries, case-normalized occupancy, and controller compatibility agree with EVC owner grouping. Existing subaccount regressions remain applicable; malformed strings outside the declared Address type are not comprehensively validated.
- `stateOverrides/{getStateOverrides,mergeStateOverrides,balanceOverrides,approvalOverrides,slotHints,accessList,index,types}.ts`: Solidity mapping order, Permit2 packed slot, chain/token cache keys, caller hints, allowance/balance probing, skip flags, and override composition. These are hypothetical RPC-state edits, never chain writes.

## Remaining limits

1. The Lean batch theorems prove a generic ordered transition/observation/failure model under **one shared finalization boundary**. The finite TypeScript checks and three Solidity examples provide correspondence evidence; they do not prove arbitrary TypeScript/EVM refinement, gas behavior, reentrancy safety or arbitrary hooks.
2. Simulation injects lens reads and synthetic native balance (default 1,000 ETH), generally forges ERC20 funding/allowances, and relies on RPC support. `canExecute` is conditional: wallet diagnostics, controller discovery and some lens reads are best effort. `snapshotReadFailures` identifies account/position read gaps but does not by itself invalidate execution. Custom `extraStateOverrides` can intentionally depart from real chain state. Successful simulation does not certify real gas funding, approval signatures, or future execution.
3. Direct calls marked `simulationMode:"independent"` must actually be independent of preceding state changes. Required approvals are requirements/preconditions, not simulated receipt-by-receipt prerequisite transactions. Multiple EVC transaction boundaries are now rejected instead of silently flattened.
4. Snapshot conversions, debt interest buffers, external quotes, token behavior and oracle/plugin freshness remain live-state assumptions. Earn's exact asset-transfer gap is fixed; its snapshot conversion/valuation limits are separately documented in the data review. Unusual tax/rebase/proxy-upgrade tokens and RPC storage-slot heuristics need token-specific validation; cached slot indices can become stale after an implementation/storage-layout change.
5. Manually authored plans with repeated finite allowance consumption, custom spenders lacking Permit2, or balance-dependent custom calls need explicit requirement aggregation and live simulation. A max approval value is treated as the built-in planners' balance-dependent sentinel during funding simulation; the SDK cannot infer arbitrary custom calldata semantics from approval metadata.
6. No live transactions, production-fork scenario matrix or complete end-to-end migration execution was performed in this execution review. The separate swap/migration review covers quote routing, external protocols and CoW submission.

## Reproduce local checks

From the SDK root:

```sh
pnpm --filter @eulerxyz/euler-v2-sdk exec vitest run test/executionService.test.ts test/simulate.test.ts test/stateOverrideComposition.test.ts test/execute.test.ts test/healthCheckSets.test.ts test/materializationIntegrity.test.ts test/materializedExecutionModel.test.ts test/materializedExecution.test.ts test/batchComposition.test.ts test/approvalOverrides.test.ts test/balanceOverrides.test.ts
pnpm --filter @eulerxyz/euler-v2-sdk typecheck
```

The focused command above passed **179 tests across 11 files**; SDK typecheck and `git diff --check` also passed. The root review records the final full-suite result.

To reproduce the actual-contract cases, use a local EVC checkout at the revision above, initialize its pinned recursive submodules, and copy `EvcSemantics.t.sol` to `test/integration/EvcSemantics.t.sol`. Then run:

```sh
forge test --root "$EVC_CHECKOUT" --match-contract SdkEvcSemanticsTest --offline -vv
node formal/integration/check-evc-abi.mjs "$EVC_CHECKOUT"
```

Recorded result: **3 passed, 0 failed**, plus **44 ABI functions matched**. Compilation used Solidity 0.8.24. `--offline` avoids Forge's optional online signature lookup; on this macOS host that lookup crashed in the system proxy library on the first run. The offline run completed successfully. These tests deploy contracts only in Forge's local EVM.
