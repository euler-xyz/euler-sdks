# Which SDK findings reach Euler Lite?

Checked public master [`e1e39e7`](https://github.com/euler-xyz/euler-lite/tree/e1e39e7d6e8cb36d5ec84aa592965c5ad35fcfb1) on 2026-09-23 and the published SDK 3.3.0 archive pinned by its lockfile. The archive integrity matches; all 182 JavaScript files match the locally installed package used in reproductions. 178 files also match normalized compilation of the originally reviewed SDK main. The four differences are export declarations and a block-pin cache-key field, not the reported mechanisms. See [package validation](/Users/kanv/Documents/euler/euler-sdks/formal/integration/recheck/lite-sdk-package-validation.json).

**The generic SDK ranking is not a Lite vulnerability ranking.** Lite bypasses several high-ranked SDK paths and adds its own guards. In particular, normal portfolio display uses onchain reads rather than the V3 adapter behind D05/D06; normal Earn withdrawals avoid E08/D01; and the main multi-intent compiler rejects the demonstrated E01 operation removal. No live incident, wallet transaction or complete browser reproduction was performed.

The prior reviewed Lite snapshot `fffb1cf` is development; current public master is `e1e39e7`. Their 13 changed files mainly concern newer preview/intent parity checks. The E01 omitted-operation count guard remains on public master. Package versions match. The final classifications below use public master.

## Evidence strength

- All 50 original finding IDs are traced, retained in 48 groups. Categories: 11 normal-feature reachable, 13 conditional/limited/guarded, 24 without a demonstrated normal UI trigger. These categories measure exposure, not exploit severity.
- 17 controlled local cases passed across four reproduction scripts. Most use the published SDK with synthetic responses; the execution script also imports the actual Lite intent factory/compiler. Some tests reproduce an SDK defect that Lite avoids, or verify a Lite guard. They are not 17 demonstrated Lite bugs.
- No current hosted deployment manifest, enabled-chain configuration, affected wallet, unusual token or live reward-row count is claimed verified.

## Practical local reproduction targets

These are reproducible fixture/fault-injection recipes. Browser steps below are proposed follow-ups, not actions already performed.

1. **E06, unnecessary approvals:** open the same Earn/Lend vault via lowercase versus checksum URL with existing finite direct approval and Permit2 enabled. Actual Lite intent construction preserves the input casing. The published resolver fixture returned 2 approval steps for lowercase versus 0 for checksum.
2. **E11, Earn approval failure:** deposit 100 units with direct approval 100, token approval to Permit2 only 95, and an unexpired Permit2 authorization to Earn for 1000. The resolver returns 0 repairs. Wallet estimation may stop the actual call before broadcast; otherwise Earn reverts. No automatic allowance repair was found at materialized dispatch.
3. **D07, hidden discovery error:** locally intercept `POST /api/internal/proxy/subgraph/{chainId}` with HTTP 200 and `{"errors":[{"message":"indexing unavailable"}]}`, then refresh portfolio. The tested SDK discovery adapter treats it as empty. No current account needs to be identified to test this error path.
4. **D11, missing aggregate rewards:** use a visible position with collateral-specific/looping rewards. The controlled 200-supplied/100-borrowed fixture returns 1% headline APY versus 2.5% individual position APY. Lite directly consumes both getters.
5. **S09, reward request loop:** return 100 rows without pagination metadata from the chain-wide reward APY endpoint. The bounded probe recorded offsets 0, 100, 200 and then deliberately aborted. Lite server vault snapshots request this chain-wide data.
6. **S10, reward decimals:** make an enabled direct/fallback Fuul or Brevis response omit token decimals for a six-decimal reward token. The published adapter fabricates 18, which Lite trusts. The controlled 1,000,000-raw-unit example becomes 1e-12 display units instead of 1. Raw claim amounts are unchanged.

## Local fixes versus Lite fixes

The SDK fixes remain uncommitted and unpushed. Lite still pins published 3.3.0. E11 approval resolution remains incomplete locally, and E07 mint estimation remains incomplete although no Lite mint UI was found. I04 also has analogous Lite-owned oracle-panel logic that ignores update results; I08 has an explicit Lite-owned V3 APY service. Updating SDK defaults alone does not establish that those Lite-owned paths are corrected.
