# Account, vault, pricing, and portfolio integration review

The [independent D01–D15 recheck](./recheck/data.md) supersedes broader interpretations of the initial descriptions below. It links each finding to the original SDK and authoritative source, distinguishes configuration hardening from ordinary failures, and records remaining limits.

Reviewed against SDK base `ff224741c251cae7673c5f835dcf3bbccd9d6605`, with local changes retained. The exact SDK files inspected are in [data-coverage.json](./data-coverage.json). Coverage means source inspection and targeted comparisons/tests, not a proof of every behavior in those files. Export/type files were checked for their public shape; bundled lens ABI tuple field order was compared mechanically with the upstream structs (21 distinct structs across 59 tuple occurrences, no mismatches or unmatched tuples). That check does not establish Solidity type/width/signedness equivalence, complete function signatures, or deployed bytecode compatibility.

Reproduce the field-order check with `node formal/integration/check-lens-structs.mjs /path/to/evk-periphery` after installing the SDK's locked development dependencies. The [checker](./check-lens-structs.mjs) reads the exact periphery commit recorded in `sources.json` using `git show`; the checkout must contain that object. It makes no network requests and does not use the checkout's current working-tree revision. Its parser covers the simple current `LensTypes.sol` struct syntax; it is not a Solidity compiler.

Upstream sources are pinned in [sources.json](./sources.json): EVK `bfb325a6e6ca09613d940b46f72ccfe017353933`, EVC `838e5f72eaea25fab7d242760245244226096054`, periphery `816c5943e5fab3a213e907dd5beaf9542305593a`, and price-oracle `bc70a37b9a22d57e5d47d144644617f9be62ba3a`. The additional EulerEarn source used here is `euler-xyz/euler-earn@ea3dacc05f4003a1326815429d70d0c77f0dabb4`. These are source references, not claims that every supported chain deploys those revisions. The V3 comparison used the downloaded OpenAPI schema, especially `AccountPosition`, `EarnVaultDetails`, batch resolve, oracle assessments, and router pagination.

## EulerEarn fee accrual: precise remaining boundary

The entity conversion fix does not make an EulerEarn snapshot equivalent to a live contract preview. [EulerEarn._convertToShares/_convertToAssets](https://github.com/euler-xyz/euler-earn/blob/ea3dacc05f4003a1326815429d70d0c77f0dabb4/src/EulerEarn.sol#L655) includes unminted performance-fee shares from `_accruedFeeAndAssets`, whereas [EulerEarnVaultLens](https://github.com/euler-xyz/evk-periphery/blob/816c5943e5fab3a213e907dd5beaf9542305593a/src/Lens/EulerEarnVaultLens.sol#L32) exposes `totalSupply` and `totalAssets` without those fee shares. Current V3 snapshots also omit the pending fee share count and `lastTotalAssets`.

The original inherited 1:1 estimate generally overestimated shares for a yield-accrued Earn vault, potentially redeeming more assets than requested or reverting for insufficient shares. The corrected snapshot formula introduced here removes that error, but still omits pending fee shares and can therefore underestimate the live share requirement. These are different mechanisms; the following shortfall example concerns the corrected snapshot formula, not the original 1:1 implementation.

A source-arithmetic reproduction uses total supply 100,000,000, total assets 120,000,000, last total assets 100,000,000, fee 20%, and virtual amount 1,000,000. Pending fee shares are 3,452,991. For 1,000,000 requested assets, the corrected snapshot formula yields 834,711 shares, while the fee-aware formula requires 863,248. Redeeming the snapshot share estimate after accrual returns 966,942 assets. This is a reproducible consequence of the source formulas conditional on outstanding fees; it is not evidence about a specific deployed vault's current fees.

The execution consumer was `executionService.resolveRedeemShares` → `planRedeem({assets})`: it encoded shares and had no onchain minimum asset amount. The execution fix now routes populated EulerEarn `planRedeem({assets})` through an exact onchain `withdraw`; explicit share redemptions remain share-denominated. See the execution review for the regression and collateral ordering. `planWithdraw` encodes exact assets, and the contract calculates required shares after accrual. `planRepayFromDeposit` and savings collateral paths do not call these conversion methods. `planMint` accepts a caller-provided exchange-rate estimate for approvals; at fixed totals, omitting pending fee shares overestimates, rather than underestimates, the needed asset approval. There are no redeem approvals.

The other production consumer is `priceService.getCollateralOraclePrice`, which converts an asset unit to shares to interpret a collateral-share oracle quote. Missing Earn fee shares can understate this fallback display price. Entity conversions and display pricing therefore remain approximations for Earn when fees are pending. An exact snapshot needs the coherent pair `(newTotalAssets, totalSupply + pendingFeeShares)` from one block, or enough fee-accrual inputs at that same block. The current lens/V3 shape does not provide that pair. A future additive live-preview API is another option; a rounded single exchange-rate scalar alone cannot reproduce exact integer conversions for every input.

## Review limits and open integration constraints

- The account "onchain" path still relies on discovery input, normally the subgraph, to find standalone deposits. Rejecting failed responses and fixing prefix batching does not discover unindexed positions, eliminate reorg/lag, or enumerate every vault for all 256 subaccounts. EVC controller/collateral arrays do not enumerate arbitrary standalone deposits.
- Missing V3 subaccount/controller metadata still carries defaults plus diagnostics. Retaining known balances is useful, but such a result is not proof that all controller state is known. Consumers must observe diagnostics and revalidate executable state.
- Some aggregate USD metrics intentionally sum available prices and can be partial when another position has no price. `populated` records an attempted population, not complete valuation. Clearing stale values improves freshness but does not turn these aggregates into complete NAV guarantees.
- `computeCurrentLTV` retains the existing zero sentinel when collateral value is zero, including positive-debt cases; the existing health-factor/liquidatable signals carry insolvency. This compatibility behavior was not redefined as infinity during the review.
- Oracle route decoding has a configured depth bound and supports the SDK's known tree schemas. This review fixes the confirmed reverse CrossAdapter path; it does not prove arbitrary recursive/custom oracle behavior. IRM decoration and APY display use JavaScript numbers and are display approximations; raw chain balances and conversion arithmetic remain BigInts.
- Securitize share conversion is 1:1 for the reviewed implementation's equal supply/internal-assets invariant; the inherited ERC4626EVC conversion itself uses virtual-adjusted totals. Securitize service enumeration is unsupported (empty lists), and `SecuritizeVaultService.factory` remains a hardcoded address marked TODO, without a chain-specific deployment source. Do not use it as general cross-chain deployment discovery.
- Per-vault RPC reads, V3 responses, strategy reads, and plugin updates are not globally pinned to one block by these services. Rate/price/state movement, hooks, paused/frozen tokens, caps, available cash, and status checks can still alter transaction feasibility. The SDK has no newly proven `maxWithdraw` availability guarantee; simulate the actual plan and preserve onchain enforcement.
- The Lean work proves explicitly stated integer arithmetic and call regrouping models, with a differential connection to selected TypeScript methods. It does not prove the TypeScript compiler, EVM execution, deployed contracts, RPC correctness, indexer completeness, market data, or every service reviewed here.
